# FeatherFence 剩余工作清单

`personal-v0.1.4-stable-20260827`（`cf3243f`）之后仍需关注的事项。它不是功能路线图；只有重新复现、
明确边界并给出验证方案的事项，才进入实现阶段。

## 1. 当前结论

- 当前没有已确认的 `main` 阻断缺陷，但上游仍有尚未完全处理的功能问题，不能概括为“没有剩余缺陷”。
- GitHub Issues 在个人仓库中处于关闭状态；上游 Issue 的状态必须另外跟踪，不能以个人仓库没有开放 Issue
  作为功能完整性的证据。
- 源码中没有待实现的 `TODO`、`FIXME` 或 `unimplemented!` 标记；测试中的 `panic!` 仅用于断言失败。
- A、B、C 已分别通过个人仓库 PR #1、#2、#3 合入，不是剩余功能。
- D 和 E 继续暂停；旧分支只作为历史证据，不直接合并、变基或复制到当前主线。
- 下一步默认是停止扩展，等待真实问题，而不是为了“继续开发”而制造重构任务。

这些项目不是已确认缺陷。只有以后修改到对应边界，或日常使用出现稳定复现时，才执行最小验证。

| 范围 | 已有证据 | 尚未完整覆盖 | 触发处理的条件 |
| --- | --- | --- | --- |
| 桌面窗口层级 | F1 已修复启动层级；冷启动、Win+D 和托盘 Zen 恢复已人工通过 | Explorer 重启、非全屏普通窗口、多显示器组合 | 再现栅栏压住普通窗口或消失 |
| 多显示器与 DPI | 有混合 DPI 位置往返修复和几何单元测试 | 显示器热插拔、主屏切换、不同缩放比例长时间使用 | 出现位置漂移、尺寸跳变或栅栏离屏 |
| 拖入/拖出交互 | 普通拖放、Ctrl 复制和同名提示曾人工通过；文件操作已有单元测试 | 跨卷端到端、非空白格释放、Explorer 异常重启中的拖放 | 出现数据语义错误、落点错误或 UI 卡顿 |
| 文件系统链接 | S6 用真实符号链接/目录联接测试覆盖复制拒绝、移动回退拒绝和清理 | OneDrive 占位文件及特殊企业同步盘的真实 UI 操作 | 正常占位文件被误拒绝，或链接被递归复制 |

验证原则：先记录稳定复现步骤、系统环境和实际结果，再决定是否修改；偶发且无法复现的视觉现象只记观察，
不直接推导代码原因。

## 4. 维护性债务

### 4.1 Clippy 既有告警

当前基线为普通目标 44 条、测试目标 47 条既有告警。它们不是功能缺陷，也不值得一次性大范围清理。
只有满足以下条件时才处理：

1. 单一机械规则；
2. 小批次、独立 PR；
3. 不改变 Win32 调用顺序、资源所有权或可见行为；
4. 告警总数只减不增。

### 4.2 大模块

`main.rs`、`fence/window.rs`、`fence/render.rs` 和 `config.rs` 仍较大，但文件长度本身不是缺陷。
只有出现明确的新依赖边界、重复生命周期或难以测试的逻辑时才继续拆分，并以降低耦合和字段可见性为验收
目标；不再做机械搬文件式重构。

## 5. 暂停事项

### 5.1 D

当前仓库没有能够独立审计的 D 规格、分支或提交，因此 D 只是历史代号，不具备继续实现的输入。
若恢复，必须先重新写清需求、非目标、数据安全边界和人工验证矩阵，再从最新 `main` 新建分支。

### 5.2 E：桌面直接落点

目标曾涉及从栅栏拖出后直接按鼠标落点提交桌面图标位置，避免先落到 Explorer 默认网格再移动。
该行为依赖 Explorer 桌面 ListView、OLE 完成时机和系统排列设置，曾出现同一环境下行为改变，尚无稳定状态
模型。

恢复 E 前至少需要：

- 明确 Explorer 自动排列、网格对齐和多选拖放下的预期；
- 区分文件移动成功与图标位置提交成功，前者不能因后者失败而回滚；
- 覆盖 Explorer 重启、多显示器、混合 DPI、跨卷、同名和非空白网格；
- 证明实现不会阻塞 UI 线程，也不会先显示默认位置再二次跳动。

在这些条件满足前，E 不进入稳定主线。

## 7. 新工作的准入顺序

后续若出现真实需求，按以下顺序处理：

1. 在当前稳定 `main` 上复现，不从旧实验分支启动；
2. 写清实际结果、预期结果、影响范围和最小人工验证；
3. 判断是产品缺陷、系统限制还是仅有体验差异；
4. 能独立解释和验证时才建新分支；
5. 只参考旧分支中的局部思路，不整体合并旧架构；
6. 完成自动检查和必要人工验证后，再决定是否提交 PR。

若没有满足以上条件的事项，当前稳定基线即为完成状态。

# FeatherFence 个人主线架构设计

本文档描述 `personal-v0.1.4-abc` 之后的目标架构和演进规则。它不是一次性重写方案，
而是后续小型、可验证 PR 的共同约束。

## 1. 当前阶段目标

个人主线进入功能冻结期，目标是：

- 保留 FeatherFence 原生 Win32、低资源占用和单进程小程序的定位；
- 修复已经确认的问题，不追求与成熟桌面整理软件的功能对齐；
- 消除全局可重入可变访问的安全风险；
- 明确持久配置、业务状态、窗口状态和平台资源的所有权；
- 让每次架构调整都能独立审查、测试和回滚；
- 为启动桌面层级修复和可选的桌面直接落点 E 提供清晰边界。

当前阶段明确不做：

- D；
- 新的桌面整理功能；
- 多 crate 工作区；
- UI 框架迁移；
- 为了“现代化”而替换已经工作的原生渲染和 OLE 拖放；
- 将实验分支整体合并回主线。

## 2. 当前结构和主要风险

### 2.1 全局状态可重入访问

当前 `Global` 存放配置、所有栅栏、窗口资源、监听器、候选文件、图标缓存和退出状态。
`with_global` 在最外层通过 `Mutex<Global>` 访问；当 Win32 模态调用导致消息重入时，
它绕过互斥锁，通过 `G_PTR` 再次构造 `&mut Global`。

这条路径可能在前一次可变借用仍然存活时创建第二个可变借用。即使所有消息都发生在 UI
线程，也不能依靠“单线程”证明重叠 `&mut` 安全。因此目标架构必须删除 `G_PTR`，并禁止
在可能重入的 Win32 调用期间持有应用状态的可变借用。

### 2.2 `Fence` 混合多类状态

当前 `Fence` 同时包含：

- 可持久化的 `FenceCfg`；
- HWND 和 DPI；
- 文件条目、分页和选择；
- hover、拖动、缩放和 OLE 拖出状态；
- 动画计时；
- 目录刷新信号；
- GDI/GDI+ 渲染缓存；
- 生命周期有效标记。

这使纯业务规则依赖窗口资源，也迫使 `Fence` 使用 `unsafe impl Send`。目标架构应把这些状态
分开，并让包含 HWND、HICON、HDC、COM 接口的类型只在 UI 线程使用。

### 2.3 `main.rs` 同时承担组合和业务

`main.rs` 目前既负责进程入口和消息循环，也负责全局状态定义、托盘命令、配置重载、文件候选
状态以及多个定时任务。目标不是把它机械切成多个同样耦合的文件，而是先确定所有权和消息流，
再把组合根以外的职责移走。

### 2.4 桌面实验缺少固定边界

稳定主线中的 `desktop_icons.rs` 主要负责桌面图标避让，规模仍可控；但桌面直接落点实验曾把
Shell View、PIDL、命中测试、后台任务、重试、取消和日志全部加入同一文件。E 若重新实现，
必须先存在明确的桌面模块边界，不能把实验文件直接搬回主线。

### 2.5 基线工具状态

Rust 1.97.1 下，v0.1.4 的测试通过，但全仓 `cargo fmt --check` 失败，clippy 也存在上游遗留
警告。后续 PR 不允许增加新警告；正式重构前先用单独的机械 PR 统一格式，避免在功能 PR 中
混入大面积格式变化。

## 3. 架构不变量

以下规则适用于后续所有实现：

1. `AppState` 只由 UI 线程拥有和修改。
2. 后台线程不能持有 `&mut AppState`、HWND 所属窗口状态、渲染缓存或未封送的 COM 接口。
3. 后台线程只产生不可变结果，通过命令队列回到 UI 线程。
4. Win32 回调只解析消息、生成命令或操作该窗口的窄状态，不直接执行跨模块业务流程。
5. 任何可能启动嵌套消息循环的调用前，必须释放应用状态借用。
6. `unsafe` 只能出现在窄的平台适配层，并在相邻注释中说明前置条件和所有权。
7. 业务和策略函数优先使用普通 Rust 类型，并保持可单元测试。
8. 持久化模型不能包含 HWND、COM、线程句柄、渲染缓存或临时交互状态。
9. 重构 PR 默认不改变可见行为；行为改变必须另开 PR。
10. 失败路径必须保持源文件、配置和内存状态可解释，不用静默覆盖换取“成功”。

## 4. 目标模块边界

目标结构按需要逐步形成，不要求一次创建所有空模块：

```text
src/
├─ main.rs                 # 进程入口、模块组合、Win32 消息循环
├─ app/
│  ├─ mod.rs
│  ├─ state.rs             # AppState 及服务所有权
│  ├─ command.rs           # AppCommand 和命令队列
│  └─ dispatch.rs          # UI 线程命令归约
├─ desktop/
│  ├─ mod.rs
│  ├─ host.rs              # Progman/WorkerW/DefView/ListView 查找与失效
│  ├─ shell_view.rs        # Shell View、PIDL 和桌面项目访问
│  ├─ avoidance.rs         # 图标禁放区、历史和撤销
│  └─ drop_position.rs     # 可选 E 的准备、提交、取消和过期判定
├─ fence/
│  ├─ mod.rs
│  ├─ model.rs             # 条目、分页、选择等纯状态
│  ├─ runtime.rs           # 单个栅栏运行期组合
│  ├─ interaction.rs       # 指针、拖动、缩放状态机
│  ├─ window.rs            # 窗口创建和消息翻译
│  ├─ layout.rs            # 几何、网格、命中测试
│  └─ render.rs            # UI 线程渲染资源
├─ transfer/
│  ├─ drag_source.rs       # OLE 拖出
│  ├─ drop_target.rs       # OLE 拖入
│  └─ file_ops.rs          # 复制、移动、重名和回滚策略
└─ storage/
   └─ config_store.rs      # 原子保存、备份和恢复
```

模块名是目标边界，不是强制一次性改名。优先移动已有代码和收窄依赖，避免同时重写算法。

## 5. 状态所有权

### 5.1 `AppState`

`AppState` 是 UI 线程唯一的应用状态根，负责组合：

- `Config`；
- `FenceRegistry`；
- 托盘和消息窗口运行状态；
- UI 线程图标缓存；
- 监听器和后台任务的所有权句柄；
- 自动收纳、下载候选和清扫重试状态；
- 退出状态。

`AppState` 不实现 `Send`。确实需要跨线程的数据必须拆成独立、可发送的值。

### 5.2 单个栅栏

单个栅栏逐步分成：

- `FenceCfg`：序列化配置；
- `FenceModel`：条目、分页、选择等不依赖 Win32 的状态；
- `FenceInteraction`：hover、按下、拖动、缩放和捕获状态；
- `FenceAnimation`：动画时间和目标；
- `FenceWindow`：HWND、DPI、刷新信号和窗口生命周期；
- `FenceRenderState`：HDC、位图和其他渲染缓存。

`FenceRuntime` 可以暂时组合这些对象，但字段访问应通过对应模块的方法完成，避免重新形成一个
所有字段都公开的大结构体。

### 5.3 后台服务

目录监听器和后续后台任务只能发送带代次的结果：

```rust
AppCommand::DirectoryChanged {
    fence_id,
    generation,
    paths,
}
```

UI 线程应用命令前检查栅栏是否仍存在、代次是否仍匹配。窗口销毁或任务取消后到达的旧结果必须
被丢弃，而不是依靠 HWND 数值恰好未复用。

## 6. 消息和命令流

目标流程：

```text
Win32 回调 / watcher / worker
            │
            ▼
      AppCommandQueue
            │ PostMessage(WM_APP_DISPATCH)
            ▼
       UI 消息窗口
            │ drain（禁止递归 drain）
            ▼
       AppState::apply
            │
            ├─ 更新纯状态
            ├─ 调用窄平台适配器
            └─ 请求重绘/保存/后续任务
```

命令队列与 `AppState` 借用分离，允许嵌套消息只追加命令。`dispatching` 守卫保证重入时不再次
归约状态；最外层处理结束后继续排空队列。

需要打开菜单、文件夹选择器、执行 OLE 拖放或销毁窗口的流程拆成三段：

1. **prepare**：短暂借用状态，复制调用所需数据；
2. **execute**：释放借用后调用可能重入的 Win32 API；
3. **complete**：把结果封装为命令，再由 UI 线程应用。

同步窗口消息若必须立即返回命中测试或光标结果，只读取该窗口的窄状态；不能在读取期间发起可能
重入的跨模块操作。

## 7. 线程和 COM 规则

| 资源 | 所有线程 | 规则 |
|---|---|---|
| HWND、窗口交互状态 | UI | 不跨线程写入 |
| GDI/GDI+ 渲染缓存 | UI | 创建、使用、销毁在同一线程 |
| OLE DropTarget/DropSource | OLE 初始化线程 | 不通过 `unsafe impl Send` 绕过线程约束 |
| Shell COM 接口 | 创建它的 apartment | 跨线程前必须显式封送；默认不跨线程 |
| `ReadDirectoryChangesW` 句柄 | watcher | 只发送路径事件，不触碰 UI 状态 |
| 文件复制/扫描结果 | worker | 返回普通值和错误，不直接显示 UI |
| 配置写入快照 | storage worker 或 UI | 写入不可变快照，完成后回报结果 |

E 如果需要后台准备桌面位置，应优先让 worker 处理纯文件系统等待和不可变数据；Shell View 提交
在拥有正确 COM apartment 的执行器中完成。不能把 UI 线程创建的 COM 接口未经封送直接移动到
普通线程。

## 8. 持久化规则

`ConfigStore` 负责：

1. 将 `Config` 序列化为内存中的完整字节；
2. 写入同目录临时文件；
3. 刷新并关闭临时文件；
4. 保留最近一份有效备份；
5. 原子替换正式配置；
6. 加载失败时尝试备份，并保留损坏文件供诊断。

保存失败不能覆盖内存中的有效配置，也不能把半个 JSON 当作新基准。

## 9. PR 演进顺序

架构 PR 固定按以下顺序推进：

1. **R0：格式基线**——记录统一 Rust 工具链，只运行 rustfmt，不改语义；
2. **R1：桌面宿主边界**——从 `utils`/`desktop_icons` 提取桌面窗口查找；
3. **R2：桌面图标避让边界**——历史、撤销和 ListView 操作进入 `desktop/avoidance`；
4. **R3：Fence 状态边界**——先拆纯模型和交互状态，不改窗口行为；
5. **R4：传输边界**——整理 OLE 协商与文件操作依赖，不改 A/B/C 语义；
6. **R5：应用命令队列**——删除 `G_PTR` 和全局重入可变访问；
7. **R6：配置存储**——原子保存、备份和恢复；
8. **F1：启动桌面层级修复**——独立行为 PR；
9. **E：桌面直接落点**——重新实现或放弃，不从实验分支整体迁移。

若某一步必须同时依赖后续步骤，先修改设计或继续缩小 PR，不通过临时全局变量维持进度。

## 10. 验证和合并标准

每个 PR 必须满足：

- 从最新个人 `main` 创建；
- 一个明确目的；
- `git diff --check` 通过；
- 全部单元测试通过；
- clippy 不增加基线警告；
- R0 之后 `cargo fmt --check` 通过；
- 纯重构 PR 的测试数量不得减少；
- 涉及 Win32 行为时列出最小人工验证矩阵；
- 不依赖未合并分支；
- 合并前说明新增 `unsafe`，正常情况应为零；
- 无法独立解释或验证的代码不合并。

个人主线使用 PR 留存设计和验证记录。上游仓库即使停止维护，也不降低个人主线的拆分标准。
